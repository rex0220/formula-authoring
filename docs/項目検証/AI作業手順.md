# 項目検証の AI の作業手順（tools の CLI で作業するとき）

このテンプレートで、**要件から kintone プラグイン「項目検証プラグイン（rex0220 field validation）Ver.72 以降」の設定 JSON を AI が生成・変更する**ときの手順です。[CLAUDE.md](../../CLAUDE.md) の指示で AI がこの文書を読みます。
項目検証の式は計算式プラグインと同じ言語で、tools は `.env` の `FORMULA_PLUGIN_ZIP`（**計算式プラグインの zip、Ver.102 以降。試用版でよい**）のエンジンで評価します（項目検証の zip は要らない）。
コマンドは `npx @rex0220/formula-authoring-tools fv <command>`（kintone には GET しか送らない。1 回に 1 つ実行する）。

## 項目検証でできること（設定の列）

| 列 | 内容 |
| --- | --- |
| 必須条件・入力不可・非表示 | 式が真のとき、その項目を必須に・入力不可に・非表示にする |
| 初期化 | 隠れたまま保存するとき、その項目を初期値に戻す（初期値が空のルックアップは解除） |
| 検証条件 | 条件の式が真のとき、メッセージの式（日・英・中）でエラーにする。上から最初の 1 つ |
| テーブル内非表示 | テーブルの子の列を隠す（テーブルの行に置く） |
| 行の追加・削除の非表示 | テーブルの ＋ / × を隠す（行 `<テーブル>($ADD)` / `($DEL)` の非表示） |
| 要素 ID の行・グループ | スペース・ラベル・罫線（要素 ID の行 `(要素ID)`）とグループを隠す |
| 共通の設定 | 有効、非表示前処理、枠線（必須で未入力・必須で入力済み・エラーの色と太さ）、NOTE と説明 |

## 要約コマンド（通信しない）

| コマンド | 出すもの |
| --- | --- |
| `npx @rex0220/formula-authoring-tools fields --app N --summary` | 項目を 1 項目 1 行で（フィールドコード、型、選択肢、ルックアップ、テーブルの子。スペース・ラベル・罫線の要素 ID は最後から 2 番目の行「項目検証の要素 ID の行」。○ と最後の行（ボタン・表示の行）は計算式プラグインのもので、項目検証では見ない） |
| `npx @rex0220/formula-authoring-tools record --app N --id R --summary` | レコードの形（値は出さない） |
| `npx @rex0220/formula-authoring-tools fv summary <設定>.json` | 項目検証の設定の要約（共通の設定、行ごとの式の有無と短い式。60 字で切る） |
| `npx @rex0220/formula-authoring-tools fv summary <設定>.json --field <code>` | 1 行の式の全文（検証条件とテーブル内非表示も） |
| `npx @rex0220/formula-authoring-tools fv diff <before>.json <after>.json` | 2 つの設定の差（共通の設定と行ごと） |

## 新しい設定を作る

1. **アプリ番号** — 要件に番号が無ければ kintone MCP の `kintone-get-apps` で探す。候補が複数あれば推測せず利用者に聞く
2. **項目** — `fields --app N` → `fields --app N --summary`。式には**ラベルでなくフィールドコード**を書く。スペース・ラベル・罫線を隠すなら要素 ID（`fields --summary` の「項目検証の要素 ID の行」。fieldcode は `"(要素ID)"`）。似たラベルは推測しない
3. **レコード** — `records --app N` で数件の形を見て、確かめに使う 1〜3 件を `record --app N --id R` で取る（条件に合うもの・合わないもの、テーブルの行があるもの）
4. **仕様の確認（設計の前）** — 表にして利用者に確かめる: どのイベントで効かせるか（作成・編集・一覧の編集。既定はどれでも）、隠したときに値を消すか（初期化）、メッセージの文と英語・中国語、ステータスの名前、テーブルは行ごとか全体か、空・未選択のときの扱い、**フォームで必須の項目は必須条件を変えられない**こと
5. **設定 JSON** — 雛形を写して**封筒**で、下書きを `temp/FV-APP<アプリ番号>-<アプリ名>.json` に書く（`settings/` と `kintone/` へは次の `fv normalize --out` で置く。Claude Code のプラグイン `formula` を入れていると、`settings/` と `kintone/` の JSON を直接書くことをフックが止めるため。項目検証の保存のツールは後の版で足す）。`pluginID` は `"rex0220 field validation plugin"`、`PluginVersion` は `"72"`、`appId` は番号。`pluginInfos` には設定を置く行だけを書き、`state: true`（「使う」）にする。式は [設定ファイル仕様.md](設定ファイル仕様.md) の「列ごとに置けない型」を守り、書き方は [検証パターン.md](検証パターン.md) から選ぶ。下の「式の決まり」を守る
6. **fv normalize** — `fv normalize temp/<ファイル>.json`（`fields/N.json` は封筒の appId から決まる）。エラーを 0 にする（下の表。直すのは `temp/` の下書き）。**警告は消さずに利用者に伝える**。エラーが無くなったら `--out settings/FV-APP<アプリ番号>-<アプリ名>.json`（計算式の設定 `APP<番号>-….json` と名前を分ける。2 回目からは `--force`）で、既定値を補った形（フォームで必須の行も入る。レイアウトの順）を置く。接続のファイルの形なら `--out` はアプリのフォルダー
7. **fv check** — `fv check settings/FV-APP<アプリ番号>-<アプリ名>.json --app N --id R --event app.record.create.show,app.record.create.submit`（編集なら `app.record.edit.…`、値の変更は `app.record.edit.change.<項目コード>`）。項目ごとの 非表示 / 入力不可 / 必須 / 誤りの文 / 保存の前に入れる値 を見て、要件どおりか確かめる。結果は模擬（kintone は変えない）で、レコードの画面とは、必須の未入力を常に文に出す・テーブルの子の隠れたルックアップも解除する・グループは出さない、が違う。画面への反映（枠線の色、グループの開閉）は実機で
8. **反映方法を伝える** — アプリの設定 → プラグイン → 項目検証プラグインの設定 → **設定をアップロード** → 取り込み方を選ぶ（設定画面の言葉「全置換」「項目の置換」で書く。設定がまだ無いアプリは「全置換」、既存の設定の一部を変えるなら「項目の置換」で対象の項目をチェック。前の設定を取り込んだか分からなければ両方を書く）→ **保存する**（「運用環境に反映」をチェックするとアプリの更新まで行う）。**既存のレコードの値は変わらない**。ただし、次に既存のレコードを編集して保存するとき、新しい必須条件・検証条件で止まることがあり、隠れて「初期化」がオンの項目は初期値に戻る — このことを必ず添える。伝える文は 1 つにまとめる（CLAUDE.md の「項目検証の設定を作った・変えた作業の最後に必ず伝える」の文に、取り込み方の場合分けと、止まりそうなレコードがあればそれを添える。同じことを 2 回書かない）

## 既存の設定を変える

1. `fv pull --app N` で今の設定を取る（API ラボの機能が有効なとき。無理なら利用者に設定画面の「設定をダウンロード」を頼み、`settings/` に置いてもらう。ダウンロードは保存値も入っているが、tools はそのまま読める）
2. `fv summary` で全体、`fv summary --field <code>` で直す行を見る
3. pull / ダウンロードのファイルは書き換えない。`fv normalize <元> --out temp/<写し>.json` で写しを作って直し、`fv normalize temp/<写し>.json --out settings/<元の名前>-edit.json` で置く。接続のファイルの形なら、`edit --app N --plugin field-validation` が `-edit.json` を作り、次のコマンドを出す（`-edit.json` を temp/ に写して直し、`--fields <アプリのフォルダー>/fields.json` を付けて `--out <…-edit.json> --force` で戻す。temp/ の下書きはアプリのフォルダーの外なので、`--fields` が要る）
4. `fv diff <元> <写し>` で差を確かめ、`fv check`
5. 反映方法は上と同じ。取り込み方は「項目の置換」で、変えた項目だけチェックしてもらう（共通の設定を変えていなければ「共通の設定」のチェックを外す）

## 設定の解説を頼まれたら

1. `fv summary <ファイル>` で行の一覧、`fv summary <ファイル> --field <code>` で式の全文を見る（設定ファイルを Read で開かない）
2. 書き方の型は [検証パターン.md](検証パターン.md) のパターン名で言う。関数は関数一覧で確かめる
3. 説明に入れること: どの項目が、どんな条件で、必須・入力不可・非表示になるか、どの検証条件でどの文が出るか、初期化で何が消えるか、イベントで変わる式（`EV_INFO`）、ユーザー・ステータスで変わる式、気づいた問題（日付を `TODAY()` と直接比べている、メッセージが `"…"` で囲まれていない、URL の文字列、「使う」がオフの行）
4. 必要なら `record` → `fv check` で、そのレコードに当てた判定を添える（模擬）
5. 分からない点は推測せず「確かめたいこと」として書く

## 計算式の手順の読み替え

[docs/AI作業手順.md](../AI作業手順.md) の「接続のファイル」「テスト用アプリとテストデータ」「要件を AI が作る」は、次を読み替えてそのまま使う。

- `pull` → `fv pull`、`normalize` → `fv normalize`、`calc` → `fv check`、`summary` / `diff` → `fv summary` / `fv diff`
- アプリのフォルダーの項目検証のダウンロード / pull は `rex0220-field-validation-app<番号>-<日時>.json`（計算式と別に、一番新しいものが今の設定）。`edit --app N --plugin field-validation`、`files --app N` は両方を出す。`take` は両方を移す
- テスト用アプリ: 項目検証のプラグインが写っていなければ、アプリの設定 → プラグインで追加してもらう
- 式の断片の試し（`try`）は計算式のサンプルアプリで動く。条件の式の結果（真か偽か）を確かめるだけなら使ってよい（更新系の関数は試さない）。項目検証の判定は `fv check`

## fv normalize の結果

`[エラー]` が 1 つでもあると書き戻さず終了コード 1（`fv check` もしない）。規則名は各行の末尾の（…）。

| エラー | 意味と直し方 |
| --- | --- |
| `schema.json` / `schema.rows` / `schema.unknown-key` / `schema.type` | JSON として読めない、行の形が違う、知らないキー（書き間違い。設定画面は黙って捨てる）、型が違う（`state` / `init` は true / false、式は文字列） |
| `schema.duplicate` | 同じ項目の行が 2 つ（1 つにまとめる） |
| `envelope.plugin` / `envelope.version` / `envelope.app` | `pluginID` が `"rex0220 field validation plugin"` でない / `PluginVersion` が 72 未満（項目検証を 72 以降にしてダウンロードし直す）/ `appId` が fields のアプリと違う |
| `plugin.version` | `.env` の計算式プラグインの zip が Ver.102 未満（利用者に新しい zip（試用版でよい）を頼む） |
| `field.missing` | 今のアプリに無い行・テーブルの子（ラベルで書いた、綴り、消えた項目、要素 ID の違い） |
| `field.column` | その型には置けない列（仕様の「列ごとに置けない型」）。例: 計算・グループに必須条件、添付に初期化、グループに検証条件 |
| `formula.update` | 更新系の関数（FSET、BUTTON、DIALOG、CLIPBORD_WRITE、EV_SET、TLTABLE、TABLE_SORT、TABLE_MAP、TABLE_DATA、CSV_TVAL）。項目検証では使わない（「使う」がオフの行でも） |
| `formula.function` / `formula.syntax` / `formula.error` | 無い関数 / 括弧・文字列が閉じていない / エンジンが評価できない（無い項目 `FIELD CODE NOT FOUND`、引数の数など。エンジンの文を読む） |
| `cond.empty` | 「使う」がオンの検証条件で、条件かメッセージ（日）が空。テーブル内非表示で式が空 |
| `size.limit` | 保存値が大きすぎる |

| 警告（消さずに利用者に伝える） | 意味 |
| --- | --- |
| `formula.strip` | 文字列の中に `//` か改行がある（保存で消えて式が切れる。URL は書かない） |
| `message.form` | メッセージが項目の値だけ（文は `"…"` で囲む。意図どおりなら残す） |
| `formula.volatile` | `TODAY` / `NOW` / `RAND` など、評価のたびに変わる関数 |

| `state.off` / `formula.off-error` | 「使う」がオフなので式が効かない / オフの行の式の誤り（オンにすると保存で止まる） |
| `border.value` | 枠線の幅・色が決まりに合わない（既定に戻る） |

## 式の決まり（守らないと動かない・壊れる）

- **封筒なしの JSON は誤り**。`pluginID` / `PluginVersion` / `appId` を書く
- 式には**フィールドコード**を書く。条件は真（true・0 以外の数・空でない文字列）のとき効く。空の式は「設定なし」
- **メッセージも式**。文は `"…"` で囲み、項目の値は `&` でつなぐ（`"金額は " & 金額 & " 円"`）。英・中が空なら日本語が出る
- **日付の項目は式の中では数（秒）**、`TODAY()` は文字列（"YYYY-MM-DD"）。`申請日 > TODAY()` は比べられない。`DATE_DIFF("TODAY", 申請日, "days") > 0` のように日数で比べ、空の日付は `AND(申請日, …)` で除く（[検証パターン.md](検証パターン.md) の P7）
- `//` から行末まではコメントで、保存のときに改行と一緒に消える。**文字列の中の `//` も消える**（`"https://…"` を書かない）
- **更新系の関数は使わない**（値を変える・テーブルを作る関数。式は表示・値の変更・保存の前・一覧の編集のたびに評価される）
- テーブルの子の式は同じ行の値を読む。テーブルの外から子を見るなら集計関数（`SUM(金額T)` など）
- 判定するのは「使う」がオンの行だけ（フォームの文字数・数値の範囲の文も、オンの行だけ）。順は 非表示 → 入力不可（隠れていれば判定しない）→ 必須（隠れても入力不可でもないとき）。文は 1 項目 1 つで、制約の文 → 検証条件 → 必須の未入力 の順
- フォームで必須の項目の必須条件は `"1"` に固定（変えられない）。ラジオボタンは kintone で常に必須
- グループを隠しても中の項目の判定は変わらない（画面で中の項目も見えなくなるだけ）
- 内部番号（`fieldno` / `ptno`）は設定画面が保存のときに付ける。tools の出力には無い（正しい）
- ログインユーザー・ステータス・イベント（`EV_INFO`）で変わる式は、どの場合にどうなるかを表にして利用者に示す（`fv check --user` / `--event`）
- `fv check` の出力には、メッセージの式の結果と初期化の値が出る（項目の値をつなぐメッセージなら、レコードの値が入る。1 つ 200 文字で切る）。確かめには、テスト用アプリのテストデータのレコードを使う（計算式の手順の「テスト用アプリとテストデータ」）

## このリポジトリのルール

[docs/AI作業手順.md](../AI作業手順.md) の「このリポジトリのルール」と同じ。kintone に書かない（tools は GET だけ、`fv check` は模擬）、`records/` と `users/` を Read で開かない、`.env` と接続のファイルを読まない・書かない、作業フォルダーの外のファイルを読まない。
