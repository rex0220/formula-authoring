# AI の作業手順（tools の CLI で作業するとき）

このテンプレートで、**要件から kintone プラグイン「計算式プラグイン（rex0220 formula）Ver.101 以降」の設定 JSON を AI が生成・変更する**ときの手順です。[CLAUDE.md](../CLAUDE.md) の指示で AI がこの文書を読みます。
コマンドは `npx @rex0220/formula-authoring-tools <command>`（tools。kintone には GET しか送らない。1 回に 1 つ実行する）。

## 読むもの（要るところだけ。全部を順に読まない）

| 知りたいこと | 読むもの |
| --- | --- |
| 設定ファイルの形（封筒、キー、既定値、書かないキー） | [docs/設定ファイル仕様.md](設定ファイル仕様.md)（機械生成。短い） |
| 雛形 | [samples/settings-source.json](../samples/settings-source.json)（テーブル内集計の例。封筒 + 元の値だけ）。項目は [samples/fields-2305.json](../samples/fields-2305.json) |
| 関数の引数と説明、使用例 | [docs/関数一覧.md](関数一覧.md) を関数名で検索（250 関数。表の後に使用例）。印（副作用 / 文脈 / ユーザー情報 / イベント / 再計算で変わる）を見る |
| **定型の計算（集計・小計・転記・行番号・初期の行・ユーザー情報 …）のやり方** | [docs/計算パターン.md](計算パターン.md) を「やりたいこと」の言葉で検索（パターン → 関数 → 式の例 → 確かめること）。関数名から探す前にこちら。✔ の例の実際の結果は [docs/計算パターン_検証.md](計算パターン_検証.md) |
| ユーザー情報の既定のテストデータ | [docs/既定のテストデータ.md](既定のテストデータ.md) |

| 項目定義・レコード・既存の設定 | 下の要約コマンド（`fields/` `records/` `settings/` の JSON を丸ごと読まない） |

## 要約コマンド（通信しない）

| コマンド | 出すもの |
| --- | --- |
| `npx @rex0220/formula-authoring-tools fields --app N --summary` | `fields/N.json` を 1 項目 1 行で（レイアウトの順。○ = 計算式を設定できる型、選択肢、ルックアップ、テーブルの子、一覧の数） |
| `npx @rex0220/formula-authoring-tools record --app N --id R --summary` | `records/N-R.json` の形（文字数・桁・テーブルの行数。値は出さない） |
| `npx @rex0220/formula-authoring-tools summary settings/<ファイル>.json` | 設定の要約（項目数、各種設定の既定との差、ボタン、一覧、権限、ランク順の計算式。80 字で切る） |
| `npx @rex0220/formula-authoring-tools summary settings/<ファイル>.json --field <code>` | 1 項目の計算式の全文 |
| `npx @rex0220/formula-authoring-tools diff <before>.json <after>.json` | 項目単位の差（★ = 既存レコードの値に影響する項目） |
| `npx @rex0220/formula-authoring-tools users --summary [--users users/<f>.json]` | ユーザー情報のテストデータの要約（人数だけ。コードや名前は出さない） |
| `npx @rex0220/formula-authoring-tools try --describe` | 同梱のサンプルアプリの項目（1 項目 1 行）とレコード 3 件の形 |

## 接続のファイル（FORMULA_KINTONE_CONFIG があるとき。複数のドメイン・アプリ）

`.env` の `FORMULA_KINTONE_CONFIG`（利用者が書く。AI は書かない）に、kintone の接続のファイル（kSQL の `ksql.config.json` と同じ形。作業フォルダーの外）がある。このときは次のとおり（無ければこの節は使わない。`.env` の 1 接続の形）。`version` が「kintone の接続: 接続のファイル …」と出せばこの形。

- 接続のファイルと、そこが名前を書いた環境変数（`env:` の参照先）は利用者のもの（秘密の値を含む）。**AI は読まない・書かない・表示しない**
- コマンドは `--profile <名前>`（省略は接続のファイルの `defaultProfile`、無ければ `dev`）と `--app <番号>`。保存先は `kintone/<profile>/<番号>-<アプリ名>/` に決まる（`--out` と `--guest` は使わない。ゲストスペースは profile で決まる）
- アプリのフォルダー: `fields.json`、`records/<番号>.json`、設定のダウンロード / pull（`rex0220-formula-app<番号>-<日時>.json`。名前はそのまま。一番新しいものが今の設定）、直したもの（`…-edit.json`）、新しい設定（その他の `*.json`。`normalize --out` の書き出し先）、印（`.formula-app.json`。tools が作る。消さない・書かない）
- フォルダーは `fields --app <番号>`、`pull`、`take` が作る（印の無いフォルダーは tools が使わない）
- 利用者が `inbox/` に置いたダウンロードは `take` でアプリのフォルダーへ移す。中身は `files --app <番号>` と `summary <ファイル>` で見る
- **ダウンロード / pull のファイルは書き換えない**。直すときは `edit --app <番号>` で `-edit.json` に写し、それを直す（`normalize --out` もこちらに）。差分は `diff <ダウンロード> <-edit.json>`
- アプリのフォルダーの中のファイルなら、`normalize` / `calc` の `--fields` は要らない（同じフォルダーの `fields.json`）。`calc` は `--id 3` で `records/3.json`
- 新しい設定は、アプリのフォルダーに `APP<番号>-<アプリ名>.json` のような名前で書く（`settings/` でなく。封筒の `appId` はそのフォルダーのアプリ）
- `users --pull` は profile の `userApiToken` か ログイン名とパスワード。出力は `users/<ホスト名>.json`（profile に依らずホスト名ごと）
- 本番のアプリも同じに扱う（読み取りだけにする守りは無い）。本番へは、利用者が開発で確かめた同じファイルを本番の設定画面でアップロードする（「項目の置換」で変えた項目だけ。アプリが違うという注意は出るが取り込める。項目が合わなければ保存のときに止まる）。**一覧 ID はアプリごとに違う**ので、一覧別設定は本番の設定画面で選び直すよう、反映方法を伝えるときに添える
- tools が「environments.json は tools 2.0.0 から使わない」で止まったら、利用者に接続のファイルへの移行を頼む（AI は書かない）

## テスト用アプリとテストデータ（kintone への書き込みの唯一の例外。利用者が明示したときだけ）

**既存のアプリのテスト用アプリは AI が作らない。** 利用者に kintone の「アプリを作成 → ほかのアプリを再利用」で複製してもらう（項目・ルックアップ・関連レコード一覧・一覧・プラグインの設定まで写り、本番と同じフィールドコードになる。「データも複製」は選ばない）。計算式プラグインが写っていなければ、アプリの設定 → プラグインで追加してもらう。

**テストデータ**（利用者が「アプリ N にテストデータを入れて」と頼んだとき）:

1. 聞く: 件数、含める値（典型でない値: 選択肢の未選択、空の金額、同じ値の重複、該当なし、0 件）、テーブルの行数
2. `fields --app N --summary` で項目と型・選択肢を見て、値を**作る**（本番のレコードは写さない。個人の名前・連絡先・実在の取引先を入れない）
3. `kintone-add-records` で N にだけ入れる（承認が出る。承認の画面のアプリ番号が N であることを確かめる）
4. 入れたレコード番号を伝え、`record --app N --id R` で取り直して `calc` に使う

**新しいアプリ**（複製元が無く、利用者が「新しいアプリを作って」と明示したとき）:

1. 聞く: アプリの名前、置くスペース（無ければ指定なし）、項目（要件から AI が案を表にして確かめる。フィールドコード・型・選択肢・テーブルの子）、テストデータの件数と含める値
2. `kintone-add-app` で作る（承認が出る）。**返ってきたアプリ番号を控え、以後はその番号にだけ書く**
3. `kintone-add-form-fields` で項目を足し（ルックアップ・関連レコード一覧は参照先を利用者に聞く）、`kintone-update-form-layout` でレイアウト、`kintone-deploy-app` で運用環境に反映（それぞれ承認が出る。承認の画面のアプリ番号が 2 の番号であることを確かめる）
4. 上の「テストデータ」の 2〜4
5. 利用者に伝える: 新しいアプリの番号と URL、**計算式プラグインをアプリの設定 → プラグインで追加してもらう**（MCP にはそのツールが無い）、以後の作業はこの番号で行う（接続のファイルの形なら profile と番号）
6. `fields --app <番号>` で項目を取ってから設定を作る

既存のアプリ（本番のアプリを含む）の項目・レイアウト・反映には、これらのツールを使わない。

## 要件を AI が作る（利用者のやりたいことが短いとき）

利用者が「アプリ N の … を集計したい」のように短く伝えただけなら、設定を作る前に**要件を `requirements/<アプリ名>.md` に書いて利用者に確かめる**（README の「作る」）。

1. `fields --app N` → `fields --app N --summary` と `records --app N` / `record --app N --id R` で、項目（フィールドコード、型、テーブルの子、選択肢）とレコードの形を見る
2. 決めるべき点を表にして聞く（「仕様の確認」と同じ観点: 該当の無い分類の行を出すか、行の順、空のときの値、端数、既存の入力値を上書きしてよい項目か、ボタンか自動か、どのイベントか、テストのレコードに無いが起こりうる値の扱い）。[docs/計算パターン.md](計算パターン.md) に同じ目的の別のやり方があれば、結果の違いを添えて選んでもらう
3. 答えをもとに [requirements/example.md](../requirements/example.md) の形で要件を書く（アプリ番号と名前、項目の対応、番号付きの要件、決めた点、未決の点）。要件はフィールドコードでなく**利用者の言葉（ラベル）**で書き、どのコードに当たるかは括弧で添える
4. 利用者が読んで OK を出してから「新しい設定を作る」に進む（要件の 4 の仕様の確認は、ここで済んだ分を繰り返さない）

## 新しい設定を作る

要件は `requirements/` のファイル（利用者が書いたもの、または上の節で AI が書いて利用者が OK したもの）、またはチャットで受け取る。

1. **アプリ番号** — 要件に番号があればそれを使う。名前だけなら kintone MCP の `kintone-get-apps` に `name` と `limit` を付けて探す。**候補が複数あれば推測せず利用者に聞く**
2. **項目** — `fields --app N` → `fields --app N --summary`。計算式には**ラベルでなくフィールドコード**を書く。要件のラベルをどのコードに対応させたかを利用者に示す。似たラベルは**推測しない**。○ の無い型（CALC、ルックアップのコピー先など）には計算式を置けない
3. **レコード** — `records --app N` で数件の形を見て、代表の 1 件（テーブルが複数行、空の項目がある）を `record --app N --id R` で取る。設定を書いた後は `record --app N --id R --fields-from settings/<ファイル>.json --force` で使う項目だけに絞ってよい
4. **仕様の確認（設計の前）** — 要件のあいまいな点と設計の選び方を、計算式を書く前に表にして利用者に確かめる（Takashi 2026-10-18「計算式を設計前に仕様確認があった方がいい」）。確かめること: 集計で該当の無い分類の行を出すか（固定の行で 0 を出す / 該当のある分類だけ）、行の順（分類の定義順 / 金額順 / 入力順）、空のときの値（空 / 0）、端数（四捨五入・切り捨て、桁）、既存の入力値を計算式で上書きしてよい項目か、ボタンで動かすか自動か、どのイベントで動くか。**テストのレコードに無いが起こりうる値**（選択肢の未選択、空の金額、同じ値の重複、該当なし、0 件）をどう扱うかも聞く（5 回目の試用で、未選択の旅費分類の扱いが式に入っていなかった。Takashi 2026-10-18）。[docs/計算パターン.md](計算パターン.md) に同じ目的の別のやり方があれば、それぞれの結果の違いを添えて選んでもらう。既存の入力値の上書き、端数、空と 0、対象の行、どのイベントで動くかは利用者の回答を待つ。それ以外の点だけ、既定の案を明示して進めてよい
5. **設定 JSON** — 雛形を写して**封筒**で `settings/APP<アプリ番号>-<アプリ名>.json` に書く（1 アプリ 1 ファイル）。`pluginID` は `"rex0220 formula plugin"`、`PluginVersion` は zip の版（`version` が出す）。`pluginInfos` に計算式を置く項目だけ書く（他は normalize が補う）。**ランクは計算の順で、大きい順に計算する**（未設定は 0、同じならレイアウトの順）。**ランクは順が逆のときだけ付ける**: ランクなし（全部 0）の計算順は テーブルの外の項目（1 回目）: 上から下、同じ行では左から右 → テーブルの中の項目: 左から右 → テーブルの外の項目（2 回目）: 上から下、同じ行では左から右（Takashi 2026-10-18）。参照される項目がこの順で先にあればランクは要らない（例: 数量・単価 → その右の金額、テーブルの金額 → テーブルの外の金額合計。Takashi 2026-10-18）。参照される項目が後ろにあるときだけ、参照される項目に大きいランクを付ける（例: 右の項目を参照する左の項目なら、右に 2、左に 1）
6. **normalize** — `normalize settings/<ファイル>.json`（`fields/N.json` は封筒の appId から決まる）。エラーを 0 にする（下の表）。**警告は消さずに利用者に伝える**。`--out settings/<ファイル>.json --force` で既定値を補った形に書き戻してよい
7. **calc** — `calc settings/<ファイル>.json --app N --id R`。項目ごとの前後を見て、要件どおりか確かめる。評価は Worker で動き、60 秒で止まる（重い式なら `--timeout 300`）。文脈が足りない（APP_URL に接続先が無い、LOOKUP_GETID の項目がルックアップでない、ログインユーザーが決まらない）ときは名指しで止まるので、利用者に聞くか `--user` を付ける。結果は模擬（レコードは更新しない）。ユーザー情報を使う式は既定のテストデータ（架空）の値、イベントで分岐する式は `--event` の文脈（既定は既存レコードを変更と同じ `allUpdate`）で計算される
8. **反映方法を伝える（4 段）** — アプリの設定 → プラグイン → 計算式プラグインの設定 → **設定をアップロード** → 取り込み方を選ぶ（設定がまだ無いアプリは「全置換」、既存の設定に項目を足すなら「項目の置換」で対象の項目をチェック）→ **保存する**（「運用環境に反映」をチェックするとアプリの更新まで行う）→ 以後に追加・編集するレコードは新しい設定で計算 → **既存のレコードは変わらない**ので、必要なら設定画面の「既存レコードを変更」か一覧の「一括計算」を利用者が実行する（★ の項目があるときは勧める）

## 既存の設定を変える

1. `pull --app N` で今の設定を `settings/APP<番号>-<アプリ名>.json` に取る（API ラボの機能が有効なとき。無理なら利用者に設定画面の「ダウンロード」を頼み `settings/` に置いてもらう）
2. `summary` で全体、`summary --field <code>` で直す項目の計算式を見る
3. pull / ダウンロードのファイルは書き換えず、写し `settings/APP<番号>-<アプリ名>-edit.json` を作って直す
4. `diff settings/<元>.json settings/<写し>.json` で差を確かめ、`normalize` と `calc`
5. 反映方法は上と同じ。取り込み方は「項目の置換」で、変えた項目だけチェックしてもらう（共通の設定を変えていなければ「共通の設定」のチェックを外す）
6. 反映したら、次の `pull`（またはダウンロード）で固定名のファイルを更新し、写し（-edit.json）は消してよいと伝える（正本は固定名のファイル）

## 計算式の解説を頼まれたら

AI が作った設定でも、設定画面からダウンロードした既存の設定（`settings/` に置いたもの、`pull` したもの、`kintone/` のアプリのフォルダーのもの）でもよい。

1. `summary <ファイル>` で項目の一覧（ランク順 = 計算順）を、`summary <ファイル> --field <code>` で解説する項目の計算式の全文を見る（設定ファイルを Read で開かない）。項目の型と選択肢は `fields --app N --summary`
2. 使っている関数の引数と意味は [docs/関数一覧.md](関数一覧.md) で確かめ、定型のやり方なら [docs/計算パターン.md](計算パターン.md) のパターン名で言う。資料に無い値や端の動きを断言するとき、資料と自分の理解が食い違うときは `try "<式>"`（下の「式の試し計算」）で実際のエンジンの結果を確かめる（推し量らない）
3. 説明に入れること: 何を計算するか（1〜2 行）、テーブルの行ごとに動くか外で動くか、計算順（ランクなしの順で合っているか）、変数（LET）の意味、条件ごとの値（例: 明細 / 小計 / それ以外）、空・未選択・該当なし・0 件のときの値、印（副作用のある関数、イベントで変わる、再計算のたびに変わる、ユーザー情報・kintone の文脈に依る）、気づいた問題（順が逆、空の扱いが無い、テストのレコードに無い値）
4. 必要なら `record --app N --id R` → `calc <ファイル> --app N --id R` で、そのレコードに当てた実際の値を添える（模擬。更新しない）
5. 分からない点（意図、アプリの運用）は推測せず「確かめたいこと」として書く

## 式の試し計算（try）

利用者のアプリの項目定義とレコードが無くても、tools に同梱の**サンプルアプリ**（架空。全項目タイプ × 2（`文字列1` / `文字列2`、`数値1` / `数値2`、`日付1` …）、テーブル 2 つ（`テーブル1` / `テーブル2`。子は `T1_数値` / `T2_文字列` のように接頭辞）、レコード 3 件 = 1 典型（全項目に値、テーブル1 3 行）/ 2 端（0、負の小数、改行、未選択、月末と年末の日付、テーブル1 1 行）/ 3 空（ほぼ全部空、テーブル 0 行））で実際の計算式エンジンの結果を見る。

- `npx @rex0220/formula-authoring-tools try "ROUND(数値1 / 3, 2)" --as NUMBER` — 式ごとに 1 行だけの設定を組んで normalize（検査）→ calc（模擬）。レコード 3 件の値（対象の型に入れた後の値と、違うときはエンジンの生の値。数値は数、日付は epoch 秒、配列は配列）と、検査のエラー・警告（構文、無い関数、副作用、文脈）が出る
- `--as` は型（`NUMBER` / `TEXT`（既定。文字列 1 行。どの値も文字列で見える）/ `DATE` / `DATETIME` / `TIME` / `DROP_DOWN` / `CHECK_BOX` / `MULTI_SELECT` / `USER_SELECT` …）か項目コード。型のときは式が参照していない項目が対象になる（`数値1` を使う式なら `数値2`）。テーブルの中で計算する（行ごと）なら `--table テーブル1`
- `--records 1,2` で絞る。文脈は calc と同じ（`--event`、`--user`、`--users`、`--mobile`。ユーザー情報は既定のテストデータ。`APP_URL` は既定の接続先 `https://example.cybozu.com`）。副作用のある関数は policy の承認が無ければ評価しない
- 項目の一覧は `try --describe`。結果は**サンプルアプリでの模擬**（利用者のアプリの項目・選択肢・レコードとは違う）。利用者の設定を確かめるのは `calc`
- スペース項目（HTML の表示）は `--as sp1`（標本のスペース項目。`SPACER` でも）で試せる。レコードに値が無いので、式の返り値（`ARRAY(ラベル, 書式, 値, 書式)` の配列や HTML）をそのまま返す。表示の確かめは実機で
- **使う場面（決まり）**: 関数の解説・使用例は資料（関数一覧・計算パターン集。✔ の例の結果は 計算パターン_検証.md）で答える。`try` を使うのは、利用者が動きの確認を求めたとき、資料に無い値や端の動き（空・範囲外・0 起点）を断言するとき、資料と自分の理解が食い違うとき。使うときは必要な式だけをまとめて（探索を続けない）
- **架空の項目と値**（利用者の項目コードや境界値で試す。値はすべて架空。実在の個人情報・本番の値は入れない）:
  - `--fields '[{"code":"単価","type":"NUMBER"},{"code":"分類","type":"DROP_DOWN","options":["明細","小計"]},{"code":"明細","type":"SUBTABLE","fields":[{"code":"金額","type":"NUMBER"}]}]'` でサンプルアプリに項目を足す（20 個まで。選択肢の型は `options` 必須。`"table":"テーブル1"` で既存のテーブルの子に。コードは標本と重ねない。独立のアプリは作れない）
  - `--data '[{"単価":100,"明細":[{"分類":"明細","金額":200}]},{"単価":0}]'` で架空の値のレコード（5 件まで。土台は `--base` の標本。既定 3 = 空）。数値は数か数字の文字列、日付 `"2026-03-31"`、日時 `"2026-03-31T00:30:00Z"`、選択肢は値（複数は配列）、ユーザーはコード、テーブルは行の配列。`--data` があるときは標本のレコードは `--records` で選んだものだけ
  - `--app N --data '…'` で利用者のアプリの項目定義（`fields/N.json` かアプリのフォルダーの `fields.json`）に架空の値を当てる（項目コード・選択肢が実機と同じ。標本のレコードは使えない。`--profile` はアプリのフォルダーの profile）
  - 結果の先頭に「足した項目（架空）」と「レコード d1: 架空の値（…）」が出る。利用者に伝えるときは架空であることを添える

## 計算式の制約（守らないと動かない・壊れる）

- **封筒なし（素の設定だけ）の JSON は誤り。** `pluginID` / `PluginVersion` が違うと取り込めない
- 計算式には**フィールドコード**を書く（ラベルではない）。テーブルの子の項目はテーブルの中の式ではそのまま、テーブルの外の式では集計関数（SUM(テーブルの子) など）で参照する
- `//` から行末まではコメント。**文字列の中の `//` も行末までコメントになる**（`"https://…"` を書かない）。改行は実行時に無視される（見やすさのために入れてよい）
- 文字列は `"…"`。`\n` は改行にならない（`\` を解釈しない）。改行は `NEWLINE()`
- **`&` は関数の結果の前後の空白を落とす**（`"sun" & IF(x, " today", "")` → `suntoday`。文字列と項目の空白は残る）。空白ごと返すなら値の全体を 1 つの文字列にする（`IF(x, "sun today", "sun")`）か `CONCAT` でつなぐ
- **`LET` は 1 つに変数を並べる**（`LET(a, 式a, b, 式b, 結果)`。後の式で前の変数を使える）。入れ子（`LET(a, …, LET(b, …))`）も動くが読みにくいので、`ARRAY_FOR` などの中で変数が要るときだけに
- 計算の順は**ランク**（-10000〜10000。**大きい順**。未設定は 0。同じならレイアウトの順）。ランクなしの計算順は テーブルの外の項目（1 回目）: 上から下、同じ行では左から右 → テーブルの中の項目: 左から右 → テーブルの外の項目（2 回目）: 上から下、同じ行では左から右。この順で合うなら付けない。参照される項目が後ろにあるときだけ、その項目のランクを大きくする。設定画面は自己参照と 2 項目の相互参照を止める（`circular_refer` が OFF）。計算は 3 段（テーブルの外 → テーブルの行 → テーブルの外をもう一度）なので、順が逆でも 2 段目で追いつくことがあるが、頼らない
- テーブル自身に計算式を置くと**行数の制御**（行数 | 初期データ）になる。テーブルの子に置くと行ごとに計算する
- 副作用のある関数は BUTTON / DIALOG の中で使う。tools は policy の承認が無ければ評価しない
- イベントで結果が変わる式（`EV_INFO("type")` など）は、どのイベントでどの値になるかを表にして利用者に示す。「既存レコードを変更」は `allUpdate`、一覧の「一括計算」は `batch` のイベントで動く（画面の入力時と同じにならない）
- 一覧 ID、権限のコード、ルックアップ先のアプリ番号は推測しない
- 内部番号（fieldno / tableno）は設定画面が保存時に補う。tools の出力には無い（正しい）

## 使えるもの（積極的に使ってよい）

- `LET(x, 式, …, 式)` で変数。`FSET(x, 値)` で LET の変数の値を変えられる（ループで積み上げる: `LET(s, "", t, ARRAY_FOR(3, i, FSET(s, s & i)), s)`）
- `REPLACEALL(項目, ARRAY(p1, r1, p2, r2, …))` / `REPLACERE(項目, ARRAY(…), "g")` で置換の組を配列で（入れ子を平らに）
- 条件付き集計 `SUMIF` / `COUNTIF` / `LASTIF` / `FIRSTIF`、テーブルの行番号 `ROWNO(テーブル)`、空の既定 `NVL`
- ユーザー情報 `UINFO(LOGIN_CODE(), "#boss")`（カスタマイズ項目は `#コード`）、`OUSERS(組織)`、`GUSERS(グループ)`（各種設定「ユーザー情報」が ON のとき）
- 関数の説明と使用例は関数一覧で名前を検索する

## このリポジトリのルール

- 封筒で出力する。`settings/` は固定名で上書きし、履歴は git で追う
- **kintone への書き込みは行わない。** tools は GET だけ、`calc` は模擬
- `records/` と `users/`（実データ）はコミットしない。作業が終わったら消してよい。どちらも Read で開かない（`record --summary` / `users --summary`。`.claude/settings.json` で拒否してある）
- 認証情報（`.env`）をファイルやチャットに書かない。`policy/` と `.env` を AI が編集しない
- tools は `.env` の `FORMULA_PLUGIN_ZIP`（計算式プラグインの zip。Ver.101 以降）から計算式エンジンと authoring API を読む。「zip の場所が分からない」「版 … には対応していない」「計算式プラグインの zip ではない」と出たら、利用者に zip の場所と版（アプリに入れたものと同じ。配布元から入手したもの）を確かめてもらう
- tools が読むファイルは作業フォルダーの中、書く先は `fields/` `records/` `settings/` `temp/` `users/` `kintone/` の下だけ（`kintone/` は接続のファイルがあるときだけ。上の「接続のファイル」の節）
- AI も作業フォルダーの外のファイルを読まない（資料は `docs/`。関数一覧・計算パターン・設定ファイル仕様に無いことは利用者に聞く）
